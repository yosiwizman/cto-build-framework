# Pilot Spec: PCI-1 — Payments / Compliance

**Type:** Validation pilot specification — pre-execution planning document
**Domain:** Payments / Compliance (PCI)
**Current status:** Untested (PCI overlay designed; no project built under governance)
**Date created:** 2026-03-18

---

## Purpose

Produce the first governed build of a project with real payment processing under PCI-compliant patterns. This pilot proves that the governance loop handles the most compliance-sensitive domain on the roadmap: tokenized payment collection, specialist review integration, and the additional evidence requirements that regulated domains impose.

---

## Current Proof Status

- PCI domain overlay is designed within governance doctrine
- No project with payment processing has been built under the governance loop
- No evidence packet, run log, or reviewer verdict exists for this domain
- The domain cannot be cited as field-tested until this pilot (or equivalent) completes

Reference: `validation/domain-matrix.md` row "Payments / Compliance" and `validation/evidence-expansion-roadmap.md` Priority 8.

---

## Scope Boundary

**In scope:**
- Integration with a real payment processor (Stripe, Square, or equivalent) using tokenized payment collection
- The application never handles raw card numbers — all card data is collected via the processor's hosted/embedded UI (Stripe Elements, Square Web Payments SDK, or equivalent)
- A complete payment flow: user enters payment details → token generated by processor → token sent to backend → charge created via processor API → confirmation displayed
- Error handling for common payment failure modes (declined card, network error, invalid amount)
- PCI scope explicitly bounded in MUST requirements — this pilot operates at SAQ A or SAQ A-EP level (tokenized, no raw card handling)
- Specialist PCI review integrated into the governance loop before release gate

**Out of scope:**
- Direct card data handling (PAN, CVV) — this pilot uses tokenization exclusively; raw card handling requires a fundamentally different PCI scope and is not in scope
- PCI DSS Level 1 certification or formal QSA audit — this pilot proves the governance loop for tokenized payments, not full PCI certification
- Recurring billing, subscriptions, or refund management — future scope
- Multi-currency or international payment compliance
- Financial reporting or accounting integration
- Fraud detection or chargeback governance
- Tax calculation or invoicing

**Dependency note:** This pilot requires a working backend (API-1) and ideally a production deployment (DEPLOY-1). Payment processing cannot be meaningfully tested against localhost alone — processor webhooks and callbacks require a reachable endpoint.

## MUST Requirements

| ID | Requirement | Verification Method |
|----|-------------|-------------------|
| PCI-1.01 | Payment UI uses the processor's hosted/embedded collection method (no raw card data touches the application) | Code review + founder verification — confirm Stripe Elements or equivalent is used |
| PCI-1.02 | Card data is tokenized by the processor before reaching the application backend | Code review — confirm backend receives token, never raw card number |
| PCI-1.03 | A successful test payment completes end-to-end (token → charge → confirmation) | Founder verification — complete a test payment using processor's test mode |
| PCI-1.04 | Declined card produces an appropriate user-facing error message | Founder verification — use processor's test decline card number |
| PCI-1.05 | Network or processor error produces an appropriate user-facing error message | Founder verification — simulate error condition per processor's test toolkit |
| PCI-1.06 | PCI scope is explicitly documented: SAQ level, what data the application handles, what it does not handle | PCI scope document on file |
| PCI-1.07 | Specialist PCI review is completed before the release gate | PCI review record on file |
| PCI-1.08 | No raw card numbers, CVVs, or PANs appear in application logs, database, or error output | Code review + log inspection |
| PCI-1.09 | The release gate includes PCI-specific criteria and produces a scored verdict | Gate result on file with PCI section |

## Exclusions / Non-Goals

- This pilot does not prove governance for direct card handling (PAN-level PCI scope)
- This pilot does not prove recurring billing or subscription governance
- This pilot does not prove fraud detection or chargeback governance
- This pilot does not constitute PCI DSS certification — it proves the governance loop for tokenized payments
- This pilot does not validate any domain beyond Payments / Compliance at the tokenized level

## Founder Verification Requirements

- Founder completes a test payment using the processor's test mode and confirms end-to-end flow
- Founder verifies that declined cards and error conditions produce appropriate user-facing messages
- Founder reviews the PCI scope document and confirms understanding of what data the application handles
- Founder confirms that the specialist PCI review was completed before the release gate
- Founder signs off on each MUST requirement individually in the evidence packet

---

## Release / Gate Criteria

The release gate must:
- Cover all 9 MUST requirements
- Include a PCI-specific section confirming: tokenization in use, no raw card data in logs/DB, SAQ level documented, specialist review completed
- Produce a scored verdict (PASS / FAIL)

A PASS requires: all MUST requirements at Proven, PCI scope document filed, specialist review record filed, and no untested MUST requirements.

---

## Specialist Review Requirements

**PCI specialist review is required for this pilot.**

This is the first domain in the validation program that mandates specialist review before the release gate. The review must be completed by a party with PCI knowledge — this may be:

- A PCI-knowledgeable developer or consultant (minimum viable)
- A Qualified Security Assessor (QSA) or Internal Security Assessor (ISA) (stronger evidence)
- The payment processor's own compliance review tools or documentation (supplementary, not sufficient alone)

The review must confirm at minimum:
- The application operates at the claimed SAQ level
- No raw card data is handled, stored, or logged by the application
- Tokenization is correctly implemented per the processor's documentation
- The PCI scope boundary is accurately documented

The level of specialist review (self-assessment with PCI knowledge, consultant review, QSA) must be stated explicitly in the review record. The claim boundary will be scoped accordingly — a QSA-reviewed pilot produces a stronger claim than a self-assessed one.
